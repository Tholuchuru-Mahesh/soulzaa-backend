1. Introduction
1.1 Purpose
Soulzaa is a global social entertainment platform that enables users to communicate, socialize, and earn through real-time voice, video, live streaming, gaming, gifting, and community-building features.
The purpose of this document is to define the product vision, business objectives, organizational hierarchy, governance model, and high-level functional scope for the Soulzaa platform. This document serves as the foundation for all subsequent functional, technical, and implementation documents.
________________________________________
1.2 Product Description
Soulzaa combines social networking, live entertainment, virtual gifting, gaming, and creator monetization into a unified platform capable of supporting millions of users worldwide.
The application provides a secure, scalable ecosystem where users can:
•	Meet new people
•	Join Audio Rooms
•	Join Video Rooms
•	Watch Live Streams
•	Host Events
•	Send Virtual Gifts
•	Play Multiplayer Games
•	Build Communities
•	Earn through Agencies
•	Purchase VIP Memberships
•	Participate in Rankings
•	Join Families (Guilds)
•	Build Creator Fanbases
________________________________________
1.3 Product Type
•	Mobile Application (Android)
•	Mobile Application (iOS)
•	Web-based Admin Panel

2. Authentication
Objective
Provide secure and seamless user authentication with multiple login options while ensuring account security and session management.
Supported Login Methods
•	Mobile Number + OTP
•	Email + Password
•	Google Login
•	Apple Login (iOS)
Functional Requirements
•	One mobile number must map to only one account.
•	Email address must be unique.
•	JWT Access Token and Refresh Token shall be issued upon successful login.
•	Sessions shall automatically expire after inactivity.
•	Admin Portal shall allow forced logout from all devices.

Validation Rules
•	Mobile number format validation.
•	Email format validation.
•	Password strength validation.
•	OTP expiry validation.
•	Maximum login attempts.
Business Rules
•	Guest accounts cannot purchase VIP.
•	Guest accounts cannot recharge coins.
•	Guest accounts cannot create rooms.
•	Guest users must register before making purchases.
Error Handling
Error	Message
Invalid OTP	OTP is incorrect.
Expired OTP	OTP has expired.
Duplicate Mobile	Mobile number already exists.
Acceptance Criteria
✓ User can log in successfully.
✓ JWT is generated.
✓ Profile loads successfully.
✓ Wallet loads successfully.
✓ Notifications sync.

1. Introduction
Purpose
This document defines the complete virtual economy and engagement systems of the Soulzaa platform, including the wallet, virtual currencies, gifting ecosystem, VIP program, experience points (EXP), family system, rankings, games, rewards, and seasonal events.
The goal is to provide a secure, scalable, and transparent economy that maximizes user engagement and creator monetization.
________________________________________2. Coin Economy
Objective
Soulzaa operates a dual-currency virtual economy.
Gold Coins
Purchased using real money.
Used for:
•	Virtual Gifts
•	VIP Membership
•	Treasure Boxes
•	Rocket Events
•	Premium Games
•	Paid Events
Restrictions:
•	Cannot be transferred between users.
•	Cannot be converted into cash.
•	Cannot be refunded after consumption.
•	Cannot become negative.
Free Coins
Earned through:
•	Daily Login
•	Daily Tasks
•	Attendance Rewards
•	Promotional Events
•	Casual Games
Used only for:
•	UNO
•	Ludo
•	Carrom
•	Domino
Restrictions:
•	Cannot purchase gifts.
•	Cannot purchase VIP.
•	Cannot open Treasure Boxes.
•	Cannot be withdrawn.
•	Cannot be converted into Gold Coins.
Business Rules
•	Every coin transaction must have a unique transaction ID.
•	All wallet transactions are immutable.
•	Wallet balances must never become negative.
•	Failed payments must not credit coins.
•	Duplicate payment callbacks must be ignored.

Backend Liability Calculation Engine
Overview

The Backend Liability Calculation Engine is the core decision-making system for all premium multiplayer games in Soulzaaa, including Greedy Food, Roulette, Lucky Fruit, and Phoenix vs Wolf.

Its primary objective is to protect the platform's virtual economy by evaluating all possible outcomes and selecting a winning result according to the configured business rules.

The client application must never calculate or influence the winning result. All calculations must be performed securely on the backend server.

Platform Profit Protection

The game engine must be designed to keep the platform profitable over time by evaluating payout liabilities for all possible outcomes and selecting the winning result according to the configured business rules.

The backend should always ensure that the platform remains financially sustainable while still providing a fair and engaging gaming experience.

This logic should remain configurable through the Admin Panel for future business requirements.

Step 1 – Close Betting

When the betting timer reaches 0 seconds:

Stop accepting new bets.
Lock all existing bets.
Save all betting transactions.
Retrieve all bets placed for the current round.

No additional bets are accepted after this point.

Step 2 – Calculate Total Bets

The backend calculates the total Gold Coins placed on every betting option for the current round.

Example:

Betting Option	Total Bet
Option A	1,000,000
Option B	3,000,000
Option C	2,500,000
Option D	500,000

The betting options differ depending on the game (Greedy Food, Roulette, Lucky Fruit, or Phoenix vs Wolf).

Step 3 – Calculate Payout Liability

For every possible winning outcome, calculate the total payout liability.

The liability is the total amount the platform would pay if that outcome becomes the winner.

Example:

If Option A wins:

Liability = Total Bet on Option A × Multiplier

If a game contains grouped outcomes (such as Veg Salad, Small Lucky, or Number Groups), the backend must calculate the combined payout for all winning bets associated with that result.

This calculation must be performed for every possible outcome.

Step 4 – Compare All Liabilities

After calculating every possible payout,

the backend compares the liability of every outcome.

Example:

Possible Result	Liability
Result A	5M
Result B	12M
Result C	18M
Result D	8M
Step 5 – Select Winning Result

By default, the backend should select the winning result with the lowest payout liability, helping the platform remain profitable over time.

The selected result is then stored as the official result for that round.

The winning result must always be generated before the client-side animation begins.

Step 6 – Generate Game Result

Depending on the game:

Greedy Food → Select winning food item or Salad.
Lucky Fruit → Select winning fruit or Lucky result.
Roulette → Select winning number (0–36).
Phoenix vs Wolf → Select winning side, then generate valid card values matching that outcome.

The generated result is sent to all connected players.

Every player receives the same result.

Step 7 – Start Result Animation

After the backend has selected the winner:

Send the result to all clients.
Start the wheel, fruit, or card animation.
Animation duration: 10 seconds.
The animation must stop exactly on the backend-selected result.

Animations are visual only.

They never determine the winner.

Step 8 – Settle Bets

After the animation finishes:

Calculate player winnings.
Credit Gold Coins to winners.
Record wallet transactions.
Update player history.
Update Top 3 Winners.
Update Live Winner Ticker.
Save round summary.
Step 9 – Store Round Information

Every completed round must be permanently stored.

Store: Only for superadmin

Security Rules
All calculations must happen on the backend.
The client application must never calculate the winning result.
The client must never calculate payouts.
Wallet balance must always be verified by the backend.
Every bet must generate a transaction record.
Every payout must generate a transaction record.
Every completed round must be permanently stored.

All game events must be recorded in audit logs.

Only the betting options, multipliers, and UI animations differ between games. By sharing a common backend engine, the platform ensures consistent behavior, simplified maintenance, improved scalability, and reduced development effort.

Soulzaa Audio Room Treasure Box / Rocket Reward System

1. Treasure Box / Rocket Reward System
A Treasure Box (or Rocket Event) will be displayed at the top of every Audio Room.

Each room contains 5 Reward Boxes.

Box Unlock Requirements
Box	Gift Coins Required
Box 1	15,000 Coins
Box 2	60,000 Coins
Box 3	200,000 Coins (2 Lakhs)
Box 4	350,000 Coins (3.5 Lakhs)
Box 5	500,000 Coins (5 Lakhs)
Unlock Logic
Boxes are unlocked only through gifts sent in the room.

Only gift coins contribute to unlocking.

Once Box 1 reaches 15,000 coins, it opens automatically.

After Box 1 opens, the counter resets to 0 for Box 2.

Box 2 starts counting from 0 to 60,000.

After Box 2 opens, the counter resets to 0 for Box 3.

Box 3 starts counting from 0 to 200,000.

After Box 3 opens, the counter resets to 0 for Box 4.

Box 4 starts counting from 0 to 350,000.

After Box 4 opens, the counter resets to 0 for Box 5.

Box 5 starts counting from 0 to 500,000.

Each box maintains its own independent progress.

Progress is visible to all users in the room.

Example:

Box 1
Progress:
12,500 / 15,000

When it reaches:

15,000 / 15,000

The box opens and the next box begins from:

0 / 60,000

2. Top Gifter Rewards
After each Treasure Box is opened, the system calculates the Top 3 Gifters who contributed toward that specific box only.

Example:

Box 1 opens.

Leaderboard is calculated only using gifts sent during the first 15,000 coins.

After Box 1 is completed, all rankings reset.

Box 2 starts with a fresh leaderboard.

The same logic applies for every box.
